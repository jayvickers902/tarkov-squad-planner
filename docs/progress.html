closed

Automated checks on every push: lint, tests, typecheck, build, bundle size. The real bug was that they ran only on pull requests while everyone commits straight to main — so the gate was decorative and essentially never fired. It now runs on push too, across the web app, the companion shell and the Rust crate. C

Security, RLS and data boundaries

closed

Row Level Security is Postgres enforcing permissions itself, so a hostile client cannot do what your UI simply does not offer. Six probes found four real holes in production: you could tick off a teammate's quest progress; any signed-in user could make themselves an admin and rewrite your curated map keys and loot; anonymous users held TRUNCATE on four tables, which no RLS policy filters at all; and pings from the previous map survived a map change. All four closed by 10_33, 10_34, 10_35 and 10_37, and verified against the live database.

done

Size limits on what the browser has to download. All six pass. The loot dataset that was over its warning line is now one file per map, and carries item ids against a per-map dictionary instead of repeating every item’s name and price at all 7,859 places it appears. The browser downloads only the map it is showing — 128.4 KiB at worst, against 843.5 KiB for the whole thing before. The largest chunk is now the quest dataset at 779.3 KiB, comfortably inside its line.

F

Scaling evidence

Every capacity number in the docs — how many clients we can carry, latency budgets, error-rate thresholds — came out of a spreadsheet model. Nothing has been measured. Replacing the guesses with data needs a staging environment and a full export of the live database schema. Blocked: that export failed on 2026‑09‑03 on Docker and database-password limits, and the linked project's applied-migration ledger is empty, so deployment history cannot be read off the filenames either. This one waits on access, not on hours.

G

Incremental realtime architecture

~20–40 h

When anything in a party changes today, every client re-fetches the whole party — all progress, every drawing, every marker, every ping — not just the thing that changed. Fine for a squad of four. It stops being fine when realtime goes unhealthy and clients fall back to polling every 15 seconds: at 10,000 visible clients that is roughly 2,333 requests a second, almost all of it data the client already had. That is not a legacy path — it is where any live client lands the moment its channel drops, and the database already shows the strain, with realtime.list_changes at 45.1% of execution time. The fix: give progress, markers, drawings and pings their own tables, send only what changed, and acknowledge a write with a small receipt instead of a whole snapshot. Schema migration, new RLS, a client rewrite, new probes and tests.

Whole-program remainder: roughly 35–70 agent hours, call it eight to fifteen sessions, and G is more than half of it. F cannot start at all until someone with database credentials and a working Docker gets the catalog dump out.

3.3

Oversized session no longer loses its newest logs

done

If your newest log session was bigger than the whole 256 MiB scan budget, the scanner skipped it and imported older sessions instead — exactly backwards. It now takes that session's newest files until the budget runs out. The fixture proves 8 files / 256 MiB, all from the newest session.
